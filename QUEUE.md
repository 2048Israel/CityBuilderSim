# The queue

The batches waiting to be done, in order, and nothing else: one line each and
a link to its brief. Jerus, 2026-10-11: "a proper md file with just the
batches queued, just indexed and as soon as a batch is done its gone from
that md fully ... just minimal info, just with links or something, not actual
stuff".

- **The top row is next.** A new batch goes on the end unless Jerus places it.
- **Done: delete the row**, in the merge that ships it. What shipped is the
  changelog's to say; this file keeps no history. Since BP1 `ship.sh` deletes
  the row in the merge and adds the rows of the batch's
  `docs/queue/<id>-ship.md`; a batch branch leaves this file alone.
- **Not done, or done in part: delete the row and put what was NOT done under
  Pending**, with why - it failed, it waits on Jerus's decision, a caveat, a
  bug. A blocked batch moves to Pending at once, pushed the same turn, so the
  next row in its lane can start (2026-10-24); the orchestrator returns it to
  Queued when its block clears, saying so in the queue commit (BP1-C ★2).
- **A Pending row leaves when Jerus reviews it**: back into the queue, or
  dropped. Besides, the orchestrator settles a row that waits only on calls
  with a recommendation, taking that way and saying which and why (Jerus,
  2026-10-23: "dont most end up being rec?"), and deletes a row the batch it
  names settled in its notes. A call so taken goes in the notes, not here.
  WHY: R1d settled four and they stayed (11-16); 9 of 20 were such (11-20).
- **No detail here.** The brief holds it - a study in `docs/studies/`, a note
  in `docs/queue/`, or a file in the project, named.
